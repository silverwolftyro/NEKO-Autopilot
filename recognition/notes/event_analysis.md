## 3. 异常模式：集中爆发

### 3.1 `BLACK_FRAME` 风暴 —— 一次持续 12 分钟的故障，被重启了 6 次

**2026-10-10 22:44:47 → 22:56:43**，跨 **6 个连续 run**：

`20261010_224447`、`224502`、`224525`、`224613`、`224759`、`225316`

| 指标 | 实测值 |
|---|---|
| 该时段 `BLACK_FRAME` + `PERCEPTION_DOWN` 事件数 | 5,300 |
| 其中 `BLACK_FRAME` 的 `context.luma` | **全部恰为 `0.0`** |
| 事件间隔中位数 | **78 ms**（≈ 12.8 Hz） |
| 间隔 p95 | 83 ms |
| > 1 秒的间隔 | 仅 5 处：14.2s / 12.3s / 34.0s / 55.2s / **198.0s** |

**关键判读**：那 5 个 >1s 的间隔**正好落在 run 交界处**。也就是说这不是 6 次独立故障，而是**同一次「画面全黑」持续了约 12 分钟，中间被手动重启了 6 次**。每个 run 内部 100% 的黑帧都落在 ≤60s 窗口内（`224759` 因 run 长 118.8s，最优 60s 窗口只覆盖 50.6%）。

**与声明 tick 率的矛盾**：全部 48 个 run 的 `CORE_STARTED.tick_rate_hz = 5.0`（5 Hz = 200ms/帧），但黑帧告警的中位间隔是 **78 ms（≈12.8 Hz）**，比声明的主循环快约 2.6 倍。数据里能确认这个数字，但**无法从 stream 判断原因**（黑帧检测是否跑在独立采集线程、日志是否去重，均不可知）。这值得排查。

94 条 `CAPTURE_FAILED` 的 `message` 里带根因，按出现顺序**换了三次**：

| 根因（`message` 原文） | 条数 | 时间段 |

## 5. 这批数据**不能**证明什么

必须写明的限制，否则上面的结论会被过度解读：

1. **run 之间硬件/配置是否一致 —— 无从得知。** stream 里没有任何硬件指纹。唯一相关线索是 `CHANNEL_DEGRADED` 只在 **3 个 run** 留痕（dxcam → bitblt），其余 **45 个 run** 的采集后端状态**完全没有记录**。
2. **不能把「后期干净」归因于「后来修好了」。** 10-09 16:59 → 10-09 23:00 之间有 **246 小时（10 天）空档**，其间是否有代码/配置/驱动改动，数据里没有记录。更关键的反证：后端在 10-10 01:37 已降级为 bitblt，但 10-10 14:14 和 17:56 **仍出现两类新的截图失败根因**，17:56 那条甚至给出了新的分辨率错误。降级并未立即消除失败。
3. **没有对照组。** 不存在「同一版本、同一后端、重复多次」的受控实验，无法区分「代码变好」与「那天恰好没开错窗口/没锁屏」。
4. **游戏窗口状态不可知。** `luma=0.0` 既可能是锁屏/息屏，也可能是窗口最小化或游戏未启动。`20261010_125648` 的暗帧（luma 2.35–5.23）又是另一种状态。两种签名**不可合并**，也**不可归因**。
5. **事件计数是节流后的，不是发生次数。** `CAPTURE_FAILED` 严格 5s 一条；`consecutive` 计数器显示实际尝试次数最高到 2,735。用条数比较「谁更严重」会失真。
6. **样本极不平衡。** 48 个 run 时长从 0.0s 到 1029.8s；短 run（<10s，共 16 个）的任何速率都不可信。`INTENT_REJECTED`、`PATHFIND_ARRIVED`、`PATHFIND_STUCK`、`TICK_CRASH`、`PANIC_KEY` 各只出现在 1 个 run，**任何跨 run 比较都没有统计意义**。
7. **无法确认 4 个缺失 `RUN_STOPPED` 的 run 是崩溃、被杀还是正常退出。** `engine_stderr.log` 未纳入本次统计。
8. **`BLACK_FRAME` 12.8 Hz 与 `tick_rate_hz=5.0` 的矛盾原因未知**（见 3.1），数据不足以判断是采集线程独立告警、日志重复，还是主循环超速。
9. **第 3.5 节的执行/拒绝矛盾无法定因**（`INTENT_REJECTED` 不带 `intent_id`）。

## 6. Demo 该展示什么 / 不该展示什么

### 6.1 该展示（说明系统真的在做事）

| 事件 | 理由 |
|---|---|
| `INTENT_EXECUTED` + `INTENT_REJECTED`（当前 run，754 + 31） | 决策 → 执行 → **限流拒绝** 的完整闭环。拒绝消息 `USE_PICKUP REJECTED: MIN_GAP:USE_PICKUP(124<800ms)` 一行就说清了策略层在工作，比任何字幕都好。 |
| `PATHFIND_START` → `PATHFIND_ARRIVED`（「已到达目标幻点 · 耗时 42s」）→ `PATHFIND_STUCK` → `ESCAPE_SUCCESS`（「脱困成功 · 已躲开死街」） | 导航 + 卡死检测 + 脱困的**完整故事线**，跨 3 个 run 能连成一段。 |
| `ENEMY_DETECTED`（20）+ `NORMAL_ATTACK`（598 条 `INTENT_EXECUTED`） | 战斗闭环。最密集的是 `20261011_000227`（17.2 分钟，15 次发现敌人 + 533 次普通攻击）。 |
| `CAPTURE_FAILED` + `CORE_PAUSED(reason=连续 10 次截图失败)` 配对 | **最有说服力的健壮性证据**：截图失败被检出 → 计数器累计 → 自动暂停执行。系统不会在看不见的时候假装在干活。 |
| `CHANNEL_DEGRADED`（dxcam → bitblt）+ 之后仍有正常 `INTENT_EXECUTED` | 「感知后端降级了，但还在跑」的韧性叙事。 |
| `ENTITY_DETECTOR_UNAVAILABLE`（93ms > 80ms 阈值，主动关闭） | **建议展示，不要藏。** 这是唯一一个「到最新一天仍然存在」的问题，拿它讲「系统知道自己的能力边界」比假装全绿更可信。 |

### 6.2 不该展示（噪声或会误导）

| 事件 | 理由 |
|---|---|
| `BLACK_FRAME` 原始刷屏（5,253 条 = 全量 **74%**） | 全部挤在一个 luma=0.0 的故障时段，对「系统在做事」零贡献。放 1 条做故障样例即可，别让它占据画面。 |
| 09-28 / 09-29 的 20 个 run（92 条，全是生命周期） | 零信息量。若要放，只放 1 条 `CORE_STARTED` 表示「跑起来了」。 |
| `CAPTURE_FAILED` 的 `consecutive` 计数器（1 → 2,735） | 看着像「崩了一万多次」，实际是**同一个持续故障被 5 秒节流后的计数器读数**，会严重误导观众。展示时请连同「5 秒一条」的说明一起，或干脆改成展示 `CORE_PAUSED` 那个瞬间。 |
| 3.5 节的 122ms vs 124ms 矛盾 | 属于待查 bug，不要在 demo 里当特性讲。 |
| `PANIC_KEY` / `PERCEPTION_BUILD_CRASH`（各 1–2 条） | 样本量太小，讲不出故事，反而暴露「只发生过一次」。 |

### 6.3 一句话定位建议

**用 `INTENT_EXECUTED` + `INTENT_REJECTED` 证明「会干活也会克制」，用 `PATHFIND_*` + `ESCAPE_SUCCESS` 证明「能规划也能自救」，用 `CAPTURE_FAILED → CORE_PAUSED` 证明「瞎了会承认瞎了」。**

## 7. 复现方式

统计脚本（只读，不写入 `_runtime`）：

```python
from pathlib import Path
import json, collections

R = Path(r"...\autopilot\_runtime")           # 被 git 忽略，必须用 pathlib 遍历
runs = {}
for f in sorted(R.glob("*.stream.jsonl")):
    runs[f.name.split(".")[0]] = [
        json.loads(L)
        for L in f.read_bytes().decode("utf-8").splitlines()   # 全 UTF-8，无需回退
        if L.strip()                                            # 空行保护
    ]

codes = collections.Counter(r["code"] for recs in runs.values() for r in recs)
# 注意：PATHFIND_START(ts_ms=0) 共 2 条异常记录，计入 codes 会让总数 = 7091，
#      做时间/速率分析时需按 ts_ms > 0 过滤。
```

关键过滤规则：`ts_ms > 0`（排除 2 条损坏记录）、run 时长排除 `20261010_013718`（10.8h 空洞）、per-minute 计算排除时长 < 10s 的 run。
