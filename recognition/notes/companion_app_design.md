> 编写时间：2026-10-03

## 〇、一句话

把感知 / 决策 / 执行三层从 N.E.K.O. 插件里**拆出来，做成用户额外下载的独立应用**，
插件通过本机 socket 调用它。

---

## 一、为什么必须独立

四条理由，前三条是工程硬约束，第四条是法律边界。

### 1.1 体积：插件撑不了

N.E.K.O. 单插件预算 3~5 MB。我们的实际依赖：

| 组件 | 体积 | 能否瘦身 |
|---|---|---|
| `bgi_world.onnx` | 10 MB | ❌ BetterGI GPL 资产，不改 |
| onnxruntime-directml | ~153 MB | ❌ 不含模型也要带运行时 |
| RapidOCR（含模型） | 数十 MB | 🟡 见 §6.2，可能可省 |
| Python 运行时 + numpy + cv2 | ~80 MB | ❌ 拆不掉 |
| **合计** | **300 MB+** | — |

即使把 OCR 换成系统自带的 WinRT（§6.2），也还有 250 MB 量级。塞进插件是不可行的。

### 1.2 依赖冲突

`onnxruntime-directml` 是**进程级原生库**。如果主程序或别的插件已经在用
`onnxruntime`（CPU / GPU / ORT 不同版本），三者共用同一个 `onnxruntime/` 目录，
装/卸任何一个都会破坏另外两个——这一点在项目里已经踩过
（依赖历史：`onnxruntime 1.25.0 → onnxruntime-gpu 1.30.0 → onnxruntime-directml 1.24.4`，
每次切换都是一次破坏）。

独立进程 = 独立的 Python 环境 = **冲突彻底消失**。

### 1.3 更新节奏

感知层现在每天都在改阈值（今天刚把实体启用阈值从 100 降到 80、
把 tap 语义从长按改成点按）。这些改动**不应该触发主程序或插件的更新**。
独立应用的更新周期可以自己定，甚至可以发布「实验通道」而不打扰稳定用户。

### 1.4 GPL 边界

BetterGI 的 `tp.json` / `bgi_*.onnx` 是 **GPL-3.0**。
N.E.K.O. 自身是 **Apache-2.0**。两者的兼容性问题在 §5 详述。

## 三、它不包含什么

划清边界比什么都重要。**越界的代价是耦合，而耦合是拆不开的。**

| 不包含 | 归谁 | 理由 |
|---|---|---|
| 角色 AI / 对话 / 情绪 / 人格 | N.E.K.O. 主体 | 这是产品灵魂，不该被一个感知进程稀释 |
| 插件协议 / 事件总线 / 任务调度 | N.E.K.O. 主体 | 那是主程序的地盘 |
| 配置界面 / 复杂 UI | 配套应用自己（极简） | 感知层是工具，不是产品 |
| 用户数据 / 游戏账号 | N.E.K.O. 主体 | 隐私敏感，物理隔离更安全 |

**配套应用里不应该有任何「对话」「性格」「讲故事」的东西。**
它只做一件事：**看屏幕、算位置、按键**。

## 四、与 N.E.K.O. 的通信方式

### 4.1 三个候选

| 方案 | 延迟 | 权限复杂度 | 调试难度 | 评价 |
|---|---|---|---|---|
| **A · 本机 socket**（127.0.0.1:PORT） | 最低 | 低（回环口无需提权） | 低（`netcat` 就能看） | ✅ 推荐 |
| B · 共享文件 / 命名管道 | 中 | 中（文件锁、清理、崩溃残留） | 中高 | ❌ |
| C · 插件做「薄客户端」转发 | 取决于底层 | 取决于底层 | 取决于底层 | ✅ 但它是 **A 的使用者**，不是独立方案 |

### 4.2 推荐：A，插件作为薄客户端

**结论：选 A。插件（C）在这个方案里扮演的角色是 socket 客户端。**

A 相对 B 的优势是决定性的：

1. **延迟可控**。socket 是双向流，可以做请求-响应；共享文件要经历「写临时文件 → 轮询 → 读 → 删」，
   光轮询周期就吃掉帧预算。
2. **没有崩溃残留**。进程崩了 socket 自然断开；共享文件会留下一堆孤儿文件，
   下次启动还得清理——而「清理逻辑本身有 bug」是经典故障源。
3. **能推送**。主程序可以主动问「现在什么状态」，也可以让配套应用主动上报
   （场景变化、契约完成）。文件方案是单向的。
4. **不污染用户目录**。B 方案会在磁盘上留下运行时产物。

### 4.3 协议草图

刻意做得**很薄**——这不是云端 API，是本机函数调用：

```
# 请求（插件 -> 配套应用）
{"op": "build",  "seq": 42}                  # 抓一帧，返回 StatePacket
{"op": "decide", "state": {...}}             # 求值规则，返回 IntentPacket
{"op": "execute","intent": {...}}            # 执行一次动作
{"op": "teleport","target_id": 1234}         # 挂起传送目标

# 响应（配套应用 -> 插件）
{"seq": 42, "ok": true, "state": {...}}
{"seq": 42, "ok": false, "error": "...", "code": "..."}
```

**为什么不用 protobuf / gRPC**：本机调用没有带宽瓶颈，
JSON 的可读性（`netcat` 直接看）在调试期的价值远大于序列化速度。
如果将来真要跨机器，再换不迟。

**超时约定**：每个请求带 `seq`，插件侧有超时（建议 200 ms）。
配套应用**不回包也是允许的**——插件记一个事件继续下一帧，不能因为感知卡住就停机。

## 五、协议边界（本文最重要的一节）

### 5.1 先纠正一个可能的误解

需求里说「集成要求会轻量很多，不用遵守那么严苛的协议约束」。
这句在**工程意义上完全成立**：

- 不再受插件体积限制
- 不再和主程序抢原生库
- 不再跟着主程序的版本节奏走
- 插件侧的接口可以设计得**极薄**（§4.3 就是例子）

但**在法律意义上，GPL 的传染性不会因为「拆成独立应用」而放松**。
这一点必须说清楚，否则设计到一半才发现要返工。

### 5.2 结论一：配套应用本体必须是 GPL-3.0

如果它**分发** `bgi_world.onnx` 和 `tp.json`（BetterGI 的 GPL-3.0 资产），
那么整个配套应用在分发时就是 GPL-3.0 的「Combined Work」。

这不是选择题，是事实。**唯一的选择是：要不要分发这些资产。**

| 方案 | 配套应用许可 | 代价 |
|---|---|---|
| **A. 分发（推荐起步）** | **GPL-3.0** | 随包带 `tp.json` + `bgi_*.onnx`，用户不用自己找 |
| B. 不分发 | Apache-2.0 可选 | 用户得自己去装 BetterGI 并配路径（我们已有探测逻辑，但体验差） |
| C. 分开发布：主程序 GPL 部分 + 用户自备资产 | 混合 | 复杂度高，不建议起步做 |

**建议先做 A。** 好处是用户开箱即用，坏处仅仅是配套应用必须开源——
而我们本来也没有闭源计划。

### 5.3 结论二：N.E.K.O. 主体可以**保持 Apache-2.0**

这是分拆的最大法律红利，也是整个方案成立的前提。

**分立的进程 + 明确定义的 IPC 接口 = 两个独立作品，不是「Combined Work」。**
这一点在著作权法里有成熟共识（也叫 "Arm's Race" 原则）：如果两个程序
只是通过网络 / 管道交换数据，它们各自的版权互不传染。

具体到我们：

- N.E.K.O.（Apache-2.0）通过 socket 发请求
- 配套应用（GPL-3.0）独立处理
- 两者**不共享代码、不链接、不内嵌**

→ **GPL 停在配套应用的边界内，不会传染到 N.E.K.O. 主体。**

⚠️ **这个结论的前提不能破坏**：
- 不能把配套应用的 Python 模块**import 进插件**
- 不能把 GPL 资产**放进 N.E.K.O. 的安装目录**
- 协议必须保持「请求-响应」形态，不能退化成「把对方的函数表传给我执行」

一旦越过这三条线，传染就成立。**代码评审时应该把这条当硬红线。**

### 5.4 结论三：绝对不能做的事

| ❌ 不能做 | 后果 |
|---|---|
| 把 `bgi_world.onnx` 塞进 N.E.K.O. 主程序目录 | Apache-2.0 项目分发 GPL 资产 = 违规 |
| 插件里 `import` 配套应用的感知模块 | 分立进程原则被打破，GPL 传染 |
| 配套应用反向依赖 N.E.K.O. 的模块 | 同上，且形成循环依赖 |
| 删掉 BetterGI 的版权声明 | 违反 GPL §5 |
| 把 `tp.json` 改名后当作自有数据发布 | 同上 |

**已经做对的**：现有的 `LICENSING.md` 已经把 GPL 资产登记在册，
`tp.json` 与 `bgi_*.onnx` 目前都是**本地保留、不随包分发**。
配套应用要分发它们时，这两条记录要同步更新。

## 六、打包方式

### 6.1 工具选择：PyInstaller（`--onedir`）

| 方案 | 评价 |
|---|---|
| **PyInstaller onedir** | ✅ 推荐。启动快、无自解压、目录结构可诊断 |
| PyInstaller onefile | ❌ 300MB 自解压到 temp，启动 10s+，且杀毒软件误报率高 |
| conda-pack | 🟡 能用但 conda 环境重，构建慢，对用户不友好 |
| 免安装 zip + 用户自带 Python | ❌ 把依赖地狱转嫁给用户 |

### 6.2 一个能省几十 MB 的决定：OCR 后端

`teleport_ocr.py` 支持两个后端：

- `rapidocr`（当前默认）——自带模型，数十 MB
- `winrt` —— **Windows 自带的 `Windows.Media.Ocr`**，零额外依赖

如果 WinRT 后端在目标机器上准确率够用（**这一点尚未验证**），
配套应用可以只带 WinRT，直接省掉几十 MB。
**建议在打包前先做一次 A/B 实测**：同一批信息框截图，两个后端各跑一遍比准确率。

### 6.3 体积预估

```
onnxruntime-directml      ~153 MB
bgi_world.onnx             ~10 MB
tp.json                    ~5 MB
Python 3.11 runtime        ~30 MB
numpy + opencv             ~80 MB
paddle/rapidocr (可选)     ~0 ~80 MB   ← 取决于 §6.2 的结论
代码 + 模板 + 配置          ~5 MB
────────────────────────────────────
合计                     ~280 ~500 MB
```

超过 300 MB 用户会有犹豫，但对比「让用户自己装 Python + 配 DirectML 驱动」，
一次性下载仍然是更好的体验。**可以用分卷或按需下载来缓解**（先下核心，
OCR 模型作为可选组件），但这属于后续优化。

### 6.4 更新机制

- **起步**：GitHub Releases + 手动下载替换整个目录
- **中期**：加一个「检查更新 → 下载 → 重启」的小界面（托盘右键）
- **不做**：自动静默更新。感知层直接影响按键行为，静默更新出问题的代价太高

## 七、命名候选

| 名字 | 中英文 | 含义 | 评价 |
|---|---|---|---|
| **N.E.K.O. Sense** | 感知 | 直白：它是 N.E.K.O. 的感知器官 | ✅ 最稳妥，用户一看就懂定位 |
| **NekoPercept** | — | 感知（Percept） | 🟡 稍文艺，但"percept"是认知科学术语，程序员友好 |
| **Iris** | 虹膜 | 眼睛 | 🟡 动听但脱离 N.E.K.O. 语境，认不出来源 |
| **Atlas** | 地图集 | 与底图 / 瓦片 / 定位强相关 | 🟡 暗示「它管地图」，容易被误解为只做定位 |
| **N.E.K.O. Body** | 躯体 | 感知 + 执行 = 身体，N.E.K.O. = 大脑 | ✅ 概念最完整：大脑负责决策，躯体负责看和动 |

**推荐 `N.E.K.O. Sense`。** 理由：它在搜索、报错提示、进程名里都能一眼认出归属，
不需要用户额外学习一个陌生词。如果将来产品线扩展（再加语音、再加手柄），
`Sense` 这个词的覆盖面也够。

## 九、明确的「不做」

- 不做云端推理 / 不上传画面 —— 隐私与带宽，且没必要
- 不做跨机器控制 —— 本机 socket 够用，跨机器会引入鉴权与安全成本
- 不追求「一次做完」—— 通信层是最容易被过度设计的地方，先用最薄的形式跑通
