## 1. 先说结构性结论：快照按设计不留历史

这不是"采集得少"，而是**采集方式决定了历史不可能存在**。代码侧证据：

| 事实 | 出处 |
|---|---|
| `write_snapshot()` 用 `atomic_write_text()` **覆盖写** `state_snapshot.json` | `autopilot/ui/writer.py:54-63` |
| 快照频率 200ms 一次，注释明写「覆盖写当前态」 | `autopilot/ui/writer.py:55-59` |
| 无轮转、无归档（`atomic_write_text` = tmp + rename，直接替换） | `autopilot/ui/writer.py:62-63` |
| 设计文档同样标注「★覆盖写（tmp+rename）」、频率 200ms | `autopilot/LOGIC_MAP.md:201`、`LOGIC_MAP.md:262` |
| 只有**事件流**有轮转（>5MB 改名 `.1`，仅保留一代）；快照无此机制 | `autopilot/ui/protocol.py:38-39` |

**后果**：48 个 run 跑了 13 天，快照文件**只可能保存最后一次写入**——即最后一个 run 跑完时的终态。中间 47 个 run 的性能数据在物理上已经不存在，不是"没采到"，是"被覆盖了"。

## 2. 平均 tick 率（tick_hz）

数据里存在**三个口径完全不同**的"速率"，必须分开看，混用会得出错误结论。

### 2.1 快照 `tick_hz` —— 真测量，但 n=1

| run_id | tick_hz | tick_count | uptime_s | 出处 |
|---|---|---|---|---|
| 20261011_180732 | **4.9** | 758 | 154.8 | `state_snapshot.json` 顶层 + `raw_stats.actual_hz` |

**分布：无法计算（n=1）。** min / 中位 / P95 / max 均不存在——不要用 4.9 去填任何一列。

内部一致性交叉验证（同一份快照 + 同一 run 的事件流）：

| 校验 | 计算 | 结果 |
|---|---|---|
| `tick_count / uptime_s` | 758 / 154.8 | **4.897 Hz** ≈ 快照 4.9 ✅ |
| 事件流 `INTENT_EXECUTED` 间隔中位数 | 203.0 ms → 1000/203 | **4.93 Hz** ≈ 快照 4.9 ✅ |
| 事件流 span vs 快照 `uptime_s` | 154.8s vs 154.8s | 完全一致 ✅ |

即：这唯一一个快照内部自洽，且与事件流独立吻合。

### 2.2 事件流 `context.tick_rate_hz` —— 是**配置值**，不是测量值

| 项目 | 数值 |
|---|---|
| 出现次数 | 48（每个 run 的 `CORE_STARTED` 各 1 条） |
| 取值分布 | **5.0 × 48（方差为 0）** |

出处：每条 `CORE_STARTED` 的 `context.tick_rate_hz`，消息为「主循环已启动（**目标** 5 Hz ≈ 200ms/帧）」。

**这是目标配置，不是实测性能。** 48 个 run 全部相同、零方差这一事实本身就说明它没有被测量填充过。拿它当性能指标会得出"13 天零波动"的假结论。

### 2.3 派生节拍（`INTENT_EXECUTED` 相邻间隔）—— 真测量，n=5 run

这是数据里**唯一能跨 run 比较的 tick 速率**。算法：取每个 run 内所有 `INTENT_EXECUTED` 的 `ts_ms` 升序排序，求相邻差值，取中位数倒数。

| run_id | 执行数 n | 真实跨度 | 间隔中位 | 间隔 P95 | 间隔最大 | 派生 Hz |
|---|---|---|---|---|---|---|
| 20261010_125648 | 5 | 0.82 s | 200.5 ms | 230.0 ms | 230.0 ms | **4.99** |
| 20261010_131350 | 55 | 12.61 s | 222.0 ms | 303.0 ms | 324.0 ms | **4.50** |
| 20261011_000227 | 533 | 185.27 s | 203.0 ms | 290.0 ms | 32811.0 ms | **4.93** |
| 20261011_175020 | 5 | 0.78 s | 201.5 ms | 206.0 ms | 206.0 ms | **4.96** |
| 20261011_180732 | 754 | 153.64 s | 203.0 ms | 293.0 ms | 329.0 ms | **4.93** |

| 统计量 | 全部 5 run | 仅 3 个样本量充足的 run（n≥55） |
|---|---|---|
| min | 4.50 | 4.50 |
| 中位 | **4.93** | **4.93** |
| P95 | 4.99 | 4.93 |
| max | 4.99 | 4.93 |
| 均值 | 4.86 | 4.79 |

**样本覆盖警告**：48 个 run 中只有 **5 个**产生了 `INTENT_EXECUTED`，其余 43 个 run 无法派生节拍；且这 5 个里有 2 个只有 5 条样本。**43/48 = 89.6% 的 run 无速率数据。**

## 3. P95 tick 耗时（ms）

### 3.1 快照口径 —— 真测量，n=1，分布不存在

| run_id | tick_avg_ms | tick_p95_ms | 出处 |
|---|---|---|---|
| 20261011_180732 | **43.06** | **142.551** | `state_snapshot.json` 顶层 + `raw_stats.avg_tick_ms` / `raw_stats.p95_tick_ms` |

**分布：无法计算（n=1）。** min / 中位 / P95 / max 在 tick 耗时上**均不存在**。表里只有 avg 和 p95 两个汇总值，没有原始样本序列，无法反推 min/max。

### 3.2 三个数字的口径关系（重要）

`tick_avg_ms = 43.06` 与 `tick_hz = 4.9` **不是同一个量**，不能互推：

| 计算 | 结果 | 说明 |
|---|---|---|
| 1000 / 43.06 | 23.22 Hz | 若把 avg 当"周期"，会得到 23 Hz，与实测 4.9 Hz 矛盾 |
| 1000 / 4.9 | 204.1 ms | 实测循环**周期** ≈ 200ms 目标预算 |
| 142.551 / 200 | **71.3%** | P95 耗时占 200ms 预算的比例 |

合理解读：`tick_avg_ms` / `tick_p95_ms` 是**每 tick 的实际计算占用时间**，而 4.9 Hz 是**含 sleep 的循环节拍**（目标 5 Hz ≈ 200ms/帧）。事件流 `INTENT_EXECUTED` 间隔中位 203ms 独立佐证了周期侧。
⚠️ 这一段是**基于三个数字的算术推断**，快照本身没有字段声明两者口径，属于解释而非数据直述。

### 3.3 不要把"间隔 P95"当成"耗时 P95"

事件流能给出的间隔分布（2.3 节表中）是**循环周期**，包含 sleep，与 142.551ms 的**计算耗时**不是同一量纲，两者不可比、不可合并成一张分布表。

## 6. 采样偏差自评

**这批快照的采样方式存在严重偏差，且不止一种。**

| # | 偏差 | 证据 | 影响 |
|---|---|---|---|
| 1 | **历史被覆盖（致命）** | 200ms 覆盖写、无归档（`writer.py:54-63`） | 13 天只留下 1 条快照，缺失率 97.92% |
| 2 | **幸存者偏差** | 存活快照来自 `20261011_180732`，其 `state=STOPPED`、`health=OK`、`tick_crashes=0`、`capture_failures=0` | 能留下的都是**跑完且干净退出**的 run；崩掉的 run 一个快照都不留 |
| 3 | **异常时无快照** | 4 个 run 缺 `RUN_STOPPED`（`20260929_164853`、`20261010_141418`、`20261010_143608`、`20261010_224525`），说明非正常结束 | 异常 run 在快照侧**完全不可见**，故障率被系统性低估 |
| 4 | **取样点固定** | 快照固定 200ms 一写，只保留最后一次 | 存活样本必然是 run 的**终态**，无法反映过程中的抖动 |
| 5 | **配对缺失** | 48 个 run 有事件流，仅 1 个有快照 | 事件流与快照无法配对，无法用流去补快照的缺失 run |
| 6 | **事件流有去重窗口** | `autopilot/tools/diag/README.md:51-54`：事件总线带 `dedupe_key` 与默认 5 秒去重窗口，"数出来的一定偏小"，2026-10-11 曾因此误判 | 基于事件计数的代理指标**偏小**，本报告 5.2 节计数均受此下限约束 |
| 7 | **流轮转丢历史** | `protocol.py:38-39`：>5MB 改名 `.1`，**只保留一代** | 当前最大流 623,921 B（占限额 12.5%），暂无轮转发生，但一旦触发最早数据即被丢弃 |
| 8 | **时间戳脏数据** | run `20261009_230025` 有 **2 条 `ts_ms=0`**（`PATHFIND_START`） | 不剔除会把该 run 时长算成 **1,791,558,099.8 秒（约 56.7 年）**。本报告统计已剔除 |
| 9 | **seq 非单调** | 约半数 run 的文件行序 ≠ seq 序 | 按文件顺序做时序分析会错；必须按 `ts_ms` 重排（本报告已重排） |
| 10 | **同毫秒多事件** | **35** 个 run 存在重复 `ts_ms`，最多一个 ms 内 4 条 | 毫秒级分辨率下不宜做严格定序 |

**文件数与 run 数是否对得上**：**对得上，但口径要说清**——目录里 48 个 `*.stream.jsonl` ↔ 48 个 `run_id`，一一对应，无孤儿、无重名。但若按"状态快照"算，**1 个快照文件 ↔ 1 个 run_id**，与其余 47 个 run 无法对应。

## 7. 这份基线**不能**用来判断什么

1. **不能判断性能是否"正常"或"有回归"。** 延迟类数据只有 1 个 run 的 1 个终态快照，且该 run 恰好是零崩溃、零抓图失败的最干净样本。任何"性能正常"的结论都是幸存者偏差的产物——**本报告不提供该结论**。
2. **不能给出 tick 耗时 / tick 率的分布。** n=1 无法产生分布。本报告表中所有 min/中位/P95/max 的空格都是**数据不足**，不是"无异常"。
3. **不能做阶段耗时归因。** 抓图、场景识别、决策、执行下发四个阶段的耗时**根本没有被采集**。无法回答"慢在抓图还是慢在决策"。
4. **不能把 `ENTITY_DETECTOR_UNAVAILABLE.measured_ms=93` 当作实体检测耗时基线。** 它是失败截尾样本（只在超标时记录），n=2 且两值相同。
5. **不能把 `tick_rate_hz=5.0` 当实测速率。** 它是 `CORE_STARTED` 的配置目标，48/48 零方差。
6. **不能跨 run 比较性能变化。** 唯一可跨 run 的派生节拍只有 5 个点，其中 2 个样本量不足，不足以识别趋势或退化点。
7. **不能评估崩溃/挂起时的性能。** 异常 run 恰恰是没有快照的那批（4 个 run 缺 `RUN_STOPPED`）。
8. **没有真机对照。** 本批全部数据来自 dry-run / 实机混合的本地运行，无基准机、无对照环境、无重复实验，"基线"一词仅指**当前唯一被存下来的那一次终态**，不具备统计意义上的基线资格。
9. **不能用事件计数反推真实频次。** 受 5 秒去重窗口影响，计数系统性偏小。

## 附录：复算方法

- 目录遍历：`pathlib.Path.iterdir()` / `glob('*.stream.jsonl')`（该目录被 `.gitignore` 以 `*` 忽略，检索工具返回空属正常，不代表不存在）
- 编码：事件流 UTF-8；`engine_stderr.log` 为 **GBK**，需 `decode('gbk')` 读取，否则中文全为乱码
- 快照 tick 率交叉验证：`tick_count / uptime_s` = 758 / 154.8 = 4.897 Hz，与 `tick_hz=4.9` 一致
- 派生节拍：`INTENT_EXECUTED` 的 `ts_ms` 升序 → 相邻差值 → 中位数 → `1000/中位数`
- P95：采用 nearest-rank（`sorted(v)[round(0.95*(n-1))]`），小样本下该定义本身不稳定，表中已标 n
- 时长统计：剔除 `ts_ms < 1577836800000`（2020-01-01 之前，即 epoch-0 脏数据）后计算
- 时区：全部按 UTC+8 呈现，与 `run_id` 文件名一致
