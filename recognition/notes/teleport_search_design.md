# 传送点模糊搜索 · 设计说明（2026-10-16）

> 对应模块：`neko_console/tabs/tpsearch.py`
> 对应测试：`tests/test_teleport_search.py`（77 条）
> 对应 UI：`neko_console/tabs/pathfind.py` 的搜索行

---

## 1. 为什么要重做

原实现 `mapdata.search_points` 只有一行实质逻辑：

```python
hits = [p for p in load_teleport_points() if key in p.search_blob]
```

**归一化后包含即命中，不排序。** 对"精确输入地名"够用，但用户实际会这么打：

| 输入形态 | 例子 | `in blob` 接得住吗 |
|---|---|---|
| 打错字 | `七天神仙` | ✗（虽有错字表，但只修 2 条） |
| 语音识别同音 | `封神像` / `离月` | ✗ |
| 拼音 | `qtsx` | ✗ |
| 只记得一半 | `风神` | ✗（且字序可能颠倒） |
| 带地区 | `蒙德 七天神像` | 部分 |

## 2. 数据形态决定了算法

`_ref_tp_sample.json`：

```
data[]  7 张地图
  └─ points[]  936 个点：{id, type, name, country, areas[], position[], tranPosition[]}
```

**关键事实：936 个点只有 106 个不同的 `name`，其中 `传送锚点` 一个名字占 777 个。**

所以：
- 单靠 name 搜必然糊成一团 → **必须把 `areas` / `country` 拼进候选串**（这就是 `(name, areas)` 联合键的由来）；
- UI 只显示 name 等于没显示 → `Candidate.label` 强制是 `名称 · 地区`。

候选串集合（与插件侧 `teleport_ocr._score_pair` 对齐）：

```
{name}  {name}-{area}  {area}  {country}  {name}-{country}
```

比插件侧多两项 `country` / `{name}-{country}`，因为 Console 用户更习惯说「蒙德的神像」。

## 3. 打分：三维度 × 一阶梯，取最高分

用户输入和地名的**书写形式**可以完全不同（用户打 `qtsx`，地名是 `七天神像`）。所以对每一侧各算三种视图，**取所有组合里的最高分**：

| 视图 | `七天神像-风` | `qtsx` |
|---|---|---|
| 中文 | `七天神像风` | `qtsx`（原样） |
| 拼音首字母 | `qtsxf` | `qtsx` |
| 拼音全拼 | `qitianshenxiangfeng` | `qtsx` |

单维度阶梯（`_ladder`）：

| 命中 | 分数 | 说明 |
|---|---|---|
| 完全相等 | 1.00 | |
| 子串 / 拼音前缀 | 0.85 | 拼音维度只认**前缀** |
| 字袋（乱序/漏字） | 0.60~0.78 | 查询的字**全部**出现在候选里（顺序无关） |
| 同音折叠后相等 | 0.78 | |
| 编辑距离 ≤ 2 | 0.55~0.75 | **按短串长度归一化** |
| difflib 相似度 ≥ 0.80 | 0.50~0.85 | |

拼音命中上限压到 **0.95**：用户直接打中文字的把握更大。

地区感知：查询里含国家名时，该国传送点 **+0.10**。

## 4. 踩过的坑（每一条都是先写错了才长出来的）

### 4.1 中文数字转阿拉伯，把数据毁了

最初 `normalize_query` 里有 `{"七": "7", ...}`，结果：

```python
normalize_query("七天神像-风")  ->  "7天神像-风"
```

**七不是数字，是专有名词的一部分。** 936 条里所有「七天神像」全被改坏，
而搜索框看不出任何异常。

现在只认一个窄到不可能伤人的模式：`第` + 单个中文数字（`第八层` → `第8层`）。

### 4.2 拼音表静默丢字，两句无关的话撞成同一个串

初版 `to_initials` 遇到表外字就跳过：

```python
to_initials("特别温暖的地方")  ==  "dd"
to_initials("zzzz不存在的地名") ==  "dd"     # z 被跳过了
```

两句毫不相干的话塌成同一串，被 `ini == ini` 判成 **0.95 分的强命中**。
这比"匹配不到"严重得多 —— 它给用户一个看起来很确定、完全错误的答案。

**教训：宁可不匹配，也不要给错的匹配。** 现在覆盖不全时整条拼音维度作废，
返回空串并被调用方跳过 —— 绝不会和另一边的空串"相等"。

### 4.3 短拼音串的双向子串

`"fs"`（风神）被判定为 `"jsxfsl"`（聚所西风戍垒）的子串 —— 两个字母在长串里偶然相邻，
拿到 0.85。拼音只可能是**开头几个字母**，所以拼音维度只做**前缀**匹配且至少 2 字母。

### 4.4 短串编辑距离没有判别力

`风像` 的首字母 `"fx"` 与 **枫丹** 的 `"fd"` 编辑距离 1 → 0.75 分，
盖过了真正该答的 `#1 七天神像-风`（0.672）。

拼音维度要动用编辑距离，至少得 4 个字母（`PYMIN_EDIT_LEN`）。

### 4.5 编辑距离没按长度归一化

`蒙度`（语音把「蒙德」听成「梦度」）：
- vs `蒙德` 改 1 字 → 正确
- vs `七天神像风` 改 2 字 → 全错

但两者绝对编辑距离都 ≤ 2，初版给的分几乎一样，正确答案被错误候选挤掉。
按短串归一化后 0.75 vs 0.55，蒙德胜出。

### 4.6 同音折叠的"重试"写成了"没命中才重试"

```python
if hit is None and q_canon != q:      # ← 错
```

`梦度` 对 `须弥` 能走 edit 维度命中 0.68，所以"已经有命中"了，
再也没机会试折叠后的 `蒙度` → 返回须弥。**弱命中挡不住正确答案，必须都算取大。**

### 4.7 预筛比只比首字母 → 全拼查询一个结果都没有

`qitianshenxiang` 的首字母视图是 `qtsxb`，预筛永远对不上，正确候选**根本不出现**。

> 预筛的目的是砍掉明显无关的。**砍错了比打分偏低严重得多** ——
> 打分低了用户还能看见，只是排序靠后；预筛砍错了用户在列表里根本找不到它。

### 4.8 预筛用 `min()` 聚合首字母 → 误杀正确候选

七天神像-冰 的候选串有「qtsxb」（七天神像冰）和「gsby」（古兽冰原），
`min()` 取到 `"gsby"`，于是 `qitianshenxiang` 被它否掉。
改成**任一候选串对上就保留**。

### 4.9 NFKC 之后 ASCII 连字符没人删

`_PUNCT_CHARS` 里只有全角 `－`，而 NFKC 会把它转成 ASCII `-` ——
转完之后反而没人删，「七天神像-风」和「七天神像风」比不上，
本该 1.0 的精确命中被拼音维度顶成 0.95。

## 5. 拼音表：手写 326 字，零新依赖

任务书要求「不引入新依赖」。环境确认：`pypinyin` / `jieba` / `rapidfuzz` **都没装**，
Console 的 `pyproject.toml` 只有 `pyside6` / `pydantic` / `tomli-w`。

`_PINYIN` 是一张手写字 → 无声调拼音表，**326 字**，覆盖传送点 **name + country**
的全部汉字（实测统计得出，不是拍脑袋）。

### 已知范围边界

**areas 的 657 个汉字不在表内。** 所以 `风起地` 的拼音维度作废（`fqd` 搜不到）。

这是刻意的取舍：areas 汉字集合 657、加上 name/country 共 774，
手写全表不现实，而**写错几个字就会造出比"搜不到"更糟的错匹配**。

扩展方式很直接：往 `_PINYIN` 补字即可，`_views` 的"覆盖不全就作废"契约会自动接手，
逻辑一行都不用改。补的时候建议用
`python -c "import json; ..."` 从 `_ref_tp_sample.json` 重新统计字符集。

## 6. 性能

| | 单次搜索（936 点） |
|---|---|
| 无缓存 | ~129 ms |
| 有缓存 + 预筛（当前） | **~28 ms** |

两处优化：
1. `_search_index`（`lru_cache`）预计算候选串 / 字符集 / 拼音视图 ——
   否则每敲一个键都要跑 ~4000 次正则；
2. 预筛：汉字查询要求至少共享一个字，拼音查询走前缀。

UI 侧再加 **250ms 防抖**，打字过程不卡。

## 7. NEKO 交互（B3）：本轮只落成字符串

Console 侧现有 IPC 只有两个方向（`bridge.py` 的模块 docstring）：

- `console_bridge.json` —— Console → 插件
- `console_commands.jsonl` —— 插件 → Console

**没有 Console → NEKO 对话的反向通道。** 按任务书约定，本轮把接缝留好：

```python
def needs_disambiguation(candidates) -> bool      # 该问吗
def build_disambiguation_question(candidates) -> str   # 问什么
```

触发线（两条任一命中）：
- top1 分数 < `AMBIGUITY_TOP_SCORE`（0.60）—— 匹配得本身不好；
- top1 与 top2 差 < `AMBIGUITY_SCORE_GAP`（0.15）—— 难兄难弟。
- 只有 1 条候选时**不**问（没得选，问了也是废话）。

UI 目前把这句话显示在地图下方的读数区：

```
你是想去【七天神像-风 · 苍风高地】还是【七天神像-风 · 风啸山坡、风起地】？
```

等反向通道就位，把 `build_disambiguation_question()` 的返回值塞进通道即可，
**调用方一行都不用改**。

## 8. 数据接入现状

**「NEKO 的返回数据」目前无处可接。** Console 没有 NEKO 对话通道，
`recognition/data/` 下也没有对话历史或用户提到的地名缓存。

模块对此是开放的：`search_teleport(query, points=...)` 的 `points` 参数
可以传任意传送点表，将来若 NEKO 侧攒出"用户之前提过的地名"，
可以构造一个加权表传进来，或在 `region_boost` 之外再加一维"对话历史加权"。
