# 真机运行环境 —— 不可写死的量

> 记录时间：2026-10-04
> 状态：**长期有效，用户已明确确认**
> 适用范围：`exports/benchmark/scripts/misc/e2e_pathfind.py` 及后续所有真机 Autopilot 脚本

## 四条硬事实

### 1. 游戏画质/帧率设置**随时会变**

用户原话：

> 后面测试，我随时会把这些画质全部都随便改，有可能中，有可能低，有可能高。

推论：**任何以「游戏帧率」为前提的常数都是猜测**。不写死，按实测值算。

### 2. 已知一次具体状态：极低画质 + 30fps

风起地那次 `--live` 就是这个配置。它是目前**唯一**一个有 fps 数字的真机记录，
所有「33.3ms/帧」类推算都来自它，且只对它成立。

### 3. 「每帧 XX ms」不能写死

| 帧率 | 一帧 |
|---|---|
| 30fps | 33.3ms |
| 60fps | 16.7ms |
| 120fps | 8.3ms |

**已经踩过的坑**：`SPLIT_SLEEP_MS = 20ms` 在 60fps 下大于一帧（拆分成立），
在 30fps 下小于一帧（8 段全被并进同一帧，**拆分等于没拆**，反倒把主循环
从 213ms 撑到 625ms，帧率 4.7→1.6，路径长度 40→5，最后 give_up）。
**在一个会变的量上赌「间隔足够大」，就是上一轮犯的错。**

同类需要按帧率推导的量：
- 单次鼠标注入的饱和上限（60px 是 30fps 下标定的）
- `TileTracker` 每帧跳变阈值（跑步每帧位移正比于帧间隔）
- 转向队列余量能跨几帧

### 4. 主循环 200ms 是**目标**，不是保证

实际帧间隔由**抓帧耗时 + 同步阻塞**决定，不由代码保证。本项目反复出现
200ms → 625ms 的塌陷，来源是 `do_escape` 的同步阻塞：

```
L1 = 400 + 700 = 1100ms      L2/L3 = 260 + 320 = 580ms      打滑 = 250ms
```

所以**所有基于「200ms 一帧」的推理都是乐观估计**，报告里必须给实测值。

## 什么时候用这份

改任何含 `SPLIT_*` / `MAX_STEP_PX` / `MOUSE_SATURATION_PX` / 帧间隔假设的代码前，
先回来读一遍。新增同类常数时，**在注释里写明它依赖哪个帧率**，
不要默默写一个数字。
